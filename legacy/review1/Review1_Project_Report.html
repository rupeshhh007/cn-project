Cross-Layer Gateway Proxy for Hardware-Fingerprinted Traffic Mitigation utilizing Transport-Layer Jitter and Application-Layer Device Telemetry

Academic Project Report — Review 1 Technical Deliverable

Domain: Computer Networks & Web Security  |  Deliverable: Review-1 Architecture & Prototype  |  Runtime: Zero-Dependency Node.js Gateway

1. Objective

The primary objective of this project is to architect, implement, and empirically validate a lightweight, high-performance gateway proxy that defends web APIs against automated scraping bots, credential-stuffing tools, and layer-7 denial-of-service traffic that actively rotates source IP addresses.

Specific technical objectives established for Review 1 include:

  • Cross-Layer Feature Extraction: Construct an in-memory observation pipeline operating at the boundary of transport timing dynamics and application-layer device signals without requiring external operating system drivers.
  • Monotonic Inter-Arrival Jitter Modeling: Utilize hardware-level monotonic CPU timers (process.hrtime.bigint()) to record nanosecond-accurate arrival intervals across a sliding sample window, computing sample mean and variance while filtering out idle inter-session pauses.
  • Coarse Feature Quantization: Formulate a discrete bucketing algorithm to normalize continuous timing and battery telemetry, preventing cryptographic avalanche divergence when hashing stochastic real-world measurements.
  • Deterministic Signature Synthesis: Generate a canonical, lexicographically sorted JSON feature representation and compute a reproducible 64-bit SHA-256 observation signature.
  • Signature-Keyed Token Bucket Rate Limiting: Implement an in-memory token bucket rate limiter keyed exclusively on the derived observation signature rather than the source IP address, demonstrating that IP-rotation evasion is neutralized.
  • Zero-Dependency Engineering: Build the prototype entirely on native Node.js core libraries (http, crypto, fs, path, url) with strict memory bounds and stream backpressure guardrails.

2. Abstract

Abstract—Automated scraping engines, credential-stuffing frameworks, and distributed denial-of-service (DDoS) networks increasingly evade perimeter web rate limiters by routing requests through decentralized residential proxy pools and rotating Layer 3/4 source IP addresses on every transaction. Conventional Web Application Firewalls (WAFs) maintain state keyed strictly to IP prefixes or volatile Layer 7 session artifacts (cookies, bearer tokens), both of which are trivially discarded by headless browser instances. This project presents the architecture, implementation, and empirical verification of a lightweight, zero-dependency cross-layer gateway proxy engineered in raw Node.js. The gateway constructs a probabilistic cross-layer observation signature by fusing two orthogonal signals: (i) application-visible request-arrival timing dynamics (inter-arrival gaps, rolling sample mean μ, and sample standard deviation σ computed via sub-microsecond monotonic clocks), and (ii) client device telemetry (battery percentage and charging state). To eliminate cryptographic avalanche divergence caused by stochastic network jitter, continuous values undergo deterministic coarse quantization (50 ms timing steps, 10% battery steps) prior to canonical JSON serialization and SHA-256 hashing. An in-memory token bucket rate limiter (capacity C = 10, refill rate r = 2.0 tokens/s) is indexed directly by the derived signature digest rather than the source IP. Empirical load testing under continuous simulated IP rotation (25 requests across 25 distinct IP addresses) demonstrates that signature stability remains invariant across IP hopping, reliably admitting requests 1–10 (HTTP 200) and enforcing deterministic throttling on requests 11–25 (HTTP 429). Critical limitations regarding network queuing noise and browser API restrictions are formally analyzed alongside a concrete roadmap for transport-layer kernel hooks in Review 2.

3. Literature Survey

Network rate limiting and perimeter device identification have evolved across distinct architectural layers, each presenting specific technical trade-offs and operational failure modes:

3.1 Network-Layer (L3/L4) Rate Limiting & IP Reputation

Traditional traffic policing relies on token bucket algorithms (RFC 2697, RFC 2698) implemented in edge gateways (e.g., Nginx, Envoy, Cloudflare). These systems key bucket states to client IPv4/IPv6 addresses or Autonomous System Numbers (ASNs). While computationally efficient, this paradigm assumes a stable 1:1 mapping between an IP address and a physical client. With the commercial proliferation of residential proxy services (e.g., Bright Data, Oxylabs) and mobile carrier Carrier-Grade NAT (CGNAT), attackers rotate through millions of valid residential IP addresses per hour. Because each rotated IP receives a dedicated, unexhausted token bucket, IP-based filtering fails completely against distributed automated attacks.

3.2 Passive Remote Physical Device Fingerprinting

Seminal work by Kohno, Broido, and claffy (IEEE TDSC 2005) demonstrated that physical devices exhibit distinct hardware clock skews caused by micro-variations in crystal oscillators. These skews can be passively estimated by inspecting TCP timestamp options (RFC 1323) across multiple packets. Paxson (1999) similarly analyzed end-to-end packet arrival dynamics to profile transport behavior. While physically sound, passive TCP fingerprinting requires low-level kernel packet capture privileges (via libpcap or raw sockets), imposing high processing overhead and architectural friction in high-throughput cloud application gateways.

3.3 Application-Layer (L7) Client Fingerprinting

Client-side web fingerprinting techniques (Eckersley 2010; Mowery and Shacham 2012) collect hardware and browser environment attributes, such as HTML5 Canvas rendering anomalies, WebGL GPU extensions, AudioContext oscillator decay, and installed system fonts. While highly discriminatory, these techniques suffer from major limitations:

  • Client Script Execution Dependency: Fingerprinting requires running heavy client-side JavaScript, which increases page latency and can be blocked by script-blocking extensions.
  • Spoofing Vulnerability: Modern headless automation frameworks (e.g., Puppeteer-extra-stealth) intercept and mock JavaScript API calls, overriding Canvas and WebGL parameters with synthetic noise.
  • Privacy & Regulatory Restrictions: Aggressive browser tracking faces increasing regulatory scrutiny (GDPR, CCPA) and active counter-measures in privacy-focused browsers (e.g., Apple Safari, Brave, Firefox).

3.4 Hardware Telemetry in Web Standards

The W3C Battery Status API was originally designed to allow web applications to conserve energy on battery-constrained mobile hardware. Olejnik et al. (2015) revealed that battery level and charging discharge rate expose short-term physical entropy capable of tracking users across short browsing sessions. While major browser vendors have subsequently restricted or deprecated unrestricted battery access on untrusted origins, device telemetry remains a valuable secondary entropy source when correlated with network timing dynamics.

3.5 Research Gap & Proposed Approach

Existing defenses operate either strictly at Layer 3/4 (vulnerable to IP hopping) or strictly at Layer 7 (vulnerable to script mocking and context clearing). There is a critical architectural void for a lightweight, cross-layer gateway that operates within the standard application runtime, passively extracts arrival timing characteristics from incoming HTTP requests, fuses them with coarse device telemetry, and enforces token-bucket rate limits without relying on source IP addresses or permanent hardware tracking.

4. Problem Statement

Modern automated bot architectures decouple Layer 3 network identity from Layer 7 application execution context. Formally, let:

R = {r_1, r_2, …, r_m}

represent a chronological sequence of malicious HTTP requests dispatched by an automated bot agent A against a target API endpoint. At each transaction i:

  1. The attacker routes request ri through an egress residential proxy node, ensuring that the apparent network source satisfies:
    IP(r_i) ≠ IP(r_j)   ∀  i ≠ j
  2. The attacker executes each request within an isolated or incognito browser context, clearing all cookies, storage tokens, and session headers:
    Cookie(r_i) = ∅   ∀  i

In a conventional rate-limiting architecture, the admission decision function fIP is indexed exclusively by source IP:

fIP(r_i) → {ALLOW, THROTTLE},    state ∈ Map⟨IP, TokenBucket⟩

Because each rotated request presents a previously unobserved IP address, the gateway initializes a fresh, fully provisioned token bucket Bnew with initial tokens equal to capacity C:

Tokens(BIP(r_i)) = C ≥ 1.0  ⇒  fIP(r_i) = ALLOW   ∀  r_i ∈ R

Consequently, the system suffers a complete mitigation failure: the attacker achieves an effective request throughput equal to the total capacity of the proxy pool, while backend database resources and authentication services are overwhelmed.

Project Problem Definition: Develop an in-memory proxy mechanism capable of mapping requests ri to an invariant or slowly varying cross-layer signature Sig(ri) derived from arrival cadence and device state, such that:

Sig(r_1) = Sig(r_2) = … = Sig(r_m)

thereby binding all m requests to a single shared token bucket and triggering automated throttling once capacity C is exhausted, irrespective of Layer 3 IP rotation.

5. Solution & Working Methodology

The proposed solution implements a multi-stage request processing pipeline inside a custom, zero-dependency Node.js HTTP gateway. The working methodology executes across eight sequential stages:

Stage 1: Connection Acceptance & Stream Backpressure

Incoming HTTP connections are received by the Node.js http.Server. To prevent memory exhaustion attacks, incoming payloads are limited to 16 KB. If accumulated chunks exceed 16 KB, the readable stream is immediately halted via req.pause(), an HTTP 413 (Payload Too Large) response is dispatched, and the underlying TCP socket is terminated (req.destroy()).

Stage 2: Monotonic Arrival Timestamp Capture

Immediately upon socket frame delivery, the gateway samples the CPU monotonic counter using process.hrtime.bigint(). Unlike wall-clock APIs, monotonic counters return nanosecond-resolution timestamps that are strictly non-decreasing and immune to Network Time Protocol (NTP) adjustments or daylight-saving clock shifts.

Stage 3: Sliding-Window Cadence Estimation & Idle Filtering

The gateway calculates the elapsed arrival gap Δtk relative to the previous request from the same logical client session. The gap is stored in a circular rolling buffer of size N = 20. To prevent intentional or accidental idle pauses from corrupting active burst measurements, an idle threshold is enforced:

Δtk ≤ 2000 ms  ⇒  Push to rolling buffer

Gaps exceeding 2000 ms are classified as session boundary resets and do not enter the active burst statistics.

Stage 4: Telemetry Ingestion & Graceful Degradation

Clients transmit device telemetry via POST /api/telemetry or inline payload fields containing battery percentage (validated between 0 and 100) and charging status (boolean). If the client browser restricts the Battery Status API, the gateway gracefully substitutes an unknown marker without interrupting request evaluation.

Stage 5: Coarse Feature Quantization

Cryptographic hash functions like SHA-256 possess the avalanche property: flipping a single bit produces an unrelated hash digest. Raw microsecond timestamps fluctuate due to kernel scheduling and local network jitter. To stabilize the signature, continuous variables are mapped into coarse floor buckets:

  • Average Cadence: Grouped into 50 ms bins: Math.floor(avgMs / 50) * 50
  • Cadence Standard Deviation: Grouped into 50 ms bins: Math.floor(stdDevMs / 50) * 50
  • Battery Level: Grouped into 10% bins: Math.floor(batteryLevel / 10) * 10

Stage 6: Canonical Serialization & Cryptographic Hashing

The quantized features are serialized into canonical JSON with lexicographically sorted keys:

{"avgIntervalBucket": 0, "batteryBucket": 70, "charging": true, "stdDevBucket": 0}

The string is processed through crypto.createHash('sha256') to produce a 64-character hexadecimal digest. The leading 12 characters are extracted as the display observation signature (e.g., e115be59193d).

Stage 7: Signature-Keyed Token Bucket Enforcement

The gateway retrieves the TokenBucket instance associated with the derived SHA-256 digest from an in-memory Map. The bucket refills fractional tokens based on elapsed monotonic time since the last refill:

Tokensnew = min(10.0, Tokensold + Δtelapsed × 2.0)

If Tokens ≥ 1.0, the request is allowed (HTTP 200), tokens decrement by 1.0, and remaining token balance and timing metrics are returned. If Tokens < 1.0, the request is throttled immediately with HTTP 429 (RATE_LIMIT_EXCEEDED).

Stage 8: Bounded In-Memory Garbage Collection

To guarantee finite memory bounds, an automated sweep executes every 60 seconds. Any client timing tracker, telemetry record, or token bucket inactive for longer than 15 minutes (TTL = 900 s) is purged from memory.

To ensure technical rigor, the project defines clear boundaries between distinct identity layers:

7. Model Description

7.1 Mathematical Formulation of Timing Estimators

Let tk represent the arrival timestamp of request k sampled via the monotonic clock in nanoseconds. The arrival delta Δtk in milliseconds is computed as:

Δtk = \frac{tk - tk-1}{10^6}   (\text{ms})

For a rolling window of N active intervals {Δt1, Δt2, …, ΔtN} where Δti ≤ 2000 ms, the sample mean μ is defined as:

μ = \frac{1}{N} \sum_{i=1}^{N} Δt_i

The sample variance s2 and sample standard deviation σ are computed using unbiased Bessel correction:

s^2 = \frac{1}{N - 1} \sum_{i=1}^{N} (Δt_i - μ)^2   (\text{for } N > 1),      σ = \sqrt{s^2}

7.2 Quantization & Canonical Signature Model

Let continuous features be denoted as μ (mean cadence), σ (jitter std dev), and B (battery level). The quantized bucket values are determined by floor division:

μ_{\text{bucket}} = \left\lfloor \frac{\max(0, μ)}{50} \right\rfloor \times 50,      σ_{\text{bucket}} = \left\lfloor \frac{\max(0, σ)}{50} \right\rfloor \times 50,      B_{\text{bucket}} = \min\left(90, \left\lfloor \frac{\max(0, B)}{10} \right\rfloor \times 10\right)

The canonical serialization string S is constructed by ordering keys lexicographically:

S = \text{JSON.stringify}(\{\text{"avgIntervalBucket"}: μ_{\text{bucket}}, \text{"batteryBucket"}: B_{\text{bucket}}, \text{"charging"}: C_{\text{state}}, \text{"stdDevBucket"}: σ_{\text{bucket}}\})

The observation signature Sig is the 12-character prefix of the SHA-256 digest:

H = \text{SHA256}(S),      Sig = H[0:12]

7.3 Token Bucket State Machine

Each unique signature Sig instantiates a token bucket governed by capacity C = 10.0, refill rate r = 2.0 tokens/s, and unit request cost w = 1.0. When request k arrives at wall-clock time tnow:

  1. Calculate elapsed seconds: Δτ = (tnow − tlastRefill) / 1000
  2. Refill bucket: Tokensrefilled = min(C, Tokenscurrent + Δτ × r)
  3. Update timestamp: tlastRefill ← tnow
  4. Evaluate admission:
    \text{Decision} = \begin{cases} \text{ALLOW (HTTP 200)}, & \text{if Tokens} \ge 1.0  ⇒  \text{Tokens} \leftarrow \text{Tokens} - 1.0 \\ \text{THROTTLE (HTTP 429)}, & \text{if Tokens} < 1.0 \end{cases}

The prototype was evaluated using an automated load test (tests/load-test.js) simulating an aggressive scraping bot dispatching 25 requests with an inter-request delay of 20 ms. Each request presented a distinct simulated source IP address (10.0.0.1 through 10.0.0.25) via the X-Demo-IP header while preserving identical device telemetry and timing cadence.

Key Empirical Findings:

  • Under standard IP rate-limiting, all 25 requests would have been admitted because each transaction reported an unobserved IP address.
  • Under the cross-layer gateway, all 25 requests mapped to the exact same observation signature (e115be59193d). The token bucket was fully depleted at request 10, and requests 11 through 25 were strictly throttled with HTTP 429.
  • Following a 2.5-second idle pause, the token bucket refilled 5.0 tokens (2.0 tokens/s × 2.5 s), and recovery requests were successfully admitted under the same signature without signature drift.

8. Limitations & Review-2 Roadmap

In adherence to academic integrity, the following limitations are formally acknowledged for the Review-1 prototype:

  • Application-Visible Timing Skew: Monotonic measurements taken inside Node.js reflect application socket delivery times, which include operating system thread scheduling delay and network queue buffering, rather than pure physical wire packet jitter.
  • Thermodynamic Nature of Battery State: Battery percentage is an ephemeral physical state rather than an immutable identifier. It correlates requests effectively across high-speed bursts but naturally changes over hours of operation.
  • Discrete Bucket Collision Boundaries: Coarse quantization introduces an edge collision probability where two distinct legitimate clients with identical battery states and similar clicking cadences map to the same bucket.

Review-2 Research Roadmap:

  1. Kernel-Level Passive TCP Probing: Incorporate eBPF (Extended Berkeley Packet Filter) or libpcap packet probes to extract true TCP handshake parameters (TCP Initial Sequence Numbers, Window Size, TCP Options order, and SYN inter-arrival jitter) directly from the network stack.
  2. Continuous Metric-Space Clustering: Replace discrete SHA-256 bucketing with Locality-Sensitive Hashing (LSH) or Euclidean distance clustering on continuous feature vectors, eliminating hard bucket boundary collisions.
  3. Empirical Benchmark Dataset: Deploy headless browser bots (Puppeteer, Playwright, Selenium) alongside real human browsing traffic to measure exact False-Positive and False-Negative detection curves.
