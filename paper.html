Cross-Layer Gateway Proxy for Hardware-Fingerprinted Traffic Mitigation utilizing Transport-Layer Jitter and Application-Layer Device Telemetry

Review-1 Architecture, Implementation, and Empirical Evaluation

Department of Computer Science and Engineering

Academic Project Review 1 — Capstone Technical Report

Abstract—Automated scraping bots, credential stuffing tools, and distributed denial-of-service (DDoS) networks increasingly evade conventional rate-limiting architectures by routing traffic through commercial residential proxy pools and rotating Layer 3/4 source addresses on a per-request basis. Conventional Web Application Firewalls (WAFs) maintain state keyed strictly to IP prefixes or volatile Layer 7 session artifacts (cookies, authorization headers), both of which are readily discarded by headless browser instances. This paper presents the architecture, implementation, and empirical verification of a lightweight, zero-dependency cross-layer gateway proxy engineered in raw Node.js. The gateway constructs a probabilistic cross-layer observation signature by fusing two orthogonal signals: (i) application-visible request-arrival timing dynamics (inter-arrival gaps, rolling sample mean μ, and sample standard deviation σ computed via sub-microsecond monotonic clocks), and (ii) client device telemetry (battery level and charging state). To mitigate cryptographic avalanche divergence caused by stochastic network jitter, continuous values undergo deterministic coarse quantization (50 ms timing bins, 10% battery bins) prior to canonical JSON serialization and SHA-256 hashing. An in-memory token bucket rate limiter (capacity C = 10, refill rate r = 2.0 tokens/s) is keyed directly to the derived 64-bit signature digest rather than the source IP. Empirical load testing under continuous simulated IP rotation (25 requests across 25 distinct IP addresses) demonstrates that signature stability remains invariant across IP hopping, reliably admitting requests 1–10 (HTTP 200) and enforcing deterministic throttling on requests 11–25 (HTTP 429). Critical limitations regarding network queuing noise and browser API restrictions are formally analyzed alongside a roadmap for transport-layer kernel hooks in Review 2.

Keywords—Rate limiting, cross-layer signature, traffic mitigation, transport jitter, token bucket, device telemetry, bot detection, IP rotation evasion.

I. Introduction

Network rate limiting is a foundational perimeter defense used to protect web applications against automated denial-of-service attacks, brute-force credential stuffing, and unauthorized resource scraping. Traditional enforcement mechanisms operate under the assumption that an individual client or machine corresponds reliably to an identifiable network identifier—predominantly an IPv4 or IPv6 address.

In contemporary threat environments, this operational assumption is invalid. Attackers routinely route malicious automated requests through decentralized residential proxy networks, cloud virtual machine pools, and cellular carrier NAT gateways, rotating the apparent client IP address on every successive HTTP transaction. Concurrently, headless automation frameworks (e.g., Puppeteer, Playwright) isolate browser contexts, discarding HTTP cookies, cache tokens, and client session identifiers between requests. Consequently, traditional rate-limiting gateways reset the token allocation for each rotated IP, granting distributed attackers near-infinite throughput while exhausting backend infrastructure.

To address this vulnerability, this research investigates cross-layer feature fusion as a basis for request correlation. Rather than attempting to establish an immutable physical silicon identifier—which is technically infeasible at the application socket layer without proprietary kernel hooks—the gateway derives a probabilistic cross-layer observation signature. By correlating high-resolution request-arrival timing characteristics with application-layer physical telemetry, the gateway correlates requests originating from the same execution environment despite continuous Layer 3 address manipulation.

II. Architectural Design & Methodology

The end-to-end request lifecycle is divided into five modular subsystems:

A. High-Resolution Monotonic Timing Tracking

Wall-clock interfaces such as Date.now() offer millisecond granularity and remain susceptible to non-monotonic clock skew and NTP time-step corrections. To capture precise arrival intervals, the gateway utilizes process.hrtime.bigint(), sampling the CPU monotonic counter at sub-microsecond resolution. For an arriving request k from client C at timestamp tk, the inter-arrival gap Δtk is given by:

Δtk = (tk - tk-1) / 106 [milliseconds]

The gateway maintains a circular buffer of the most recent N = 20 arrival intervals. An idle gap threshold (Δt > 2000 ms) filters session boundary pauses from active burst cadences. Statistical estimators are evaluated over the window:

μ = (1 / N) ∑ Δti    |    s2 = (1 / (N - 1)) ∑ (Δti - μ)2    |    σ = √(s2)

B. Application-Layer Telemetry Ingestion

Clients transmit physical device telemetry comprising battery level B ∈ [0, 100] and charging status Cstate ∈ {true, false}. When browser security restrictions prevent access to the W3C Battery Status API, the gateway gracefully falls back to an unknown marker without halting execution, preserving timing-only correlation.

C. Coarse Quantization & Deterministic Serialization

Cryptographic hashing functions such as SHA-256 exhibit the avalanche effect: a microsecond timing fluctuation would alter the entire digest. To ensure signature stability, continuous feature vectors are discretized into coarse bins:

Bbucket = ⌊B / 10⌋ × 10   |   μbucket = ⌊μ / 50⌋ × 50   |   σbucket = ⌊σ / 50⌋ × 50

The quantized parameters are serialized into canonical JSON with lexicographically sorted keys: {"avgIntervalBucket": μb, "batteryBucket": Bb, "charging": Cs, "stdDevBucket": σb}. The SHA-256 hash is computed, with the leading 12 hexadecimal characters extracted as the display signature.

D. Signature-Keyed Token Bucket Rate Limiter

Each derived signature maps to an independent token bucket instance parameterized by capacity C = 10.0 tokens, refill rate r = 2.0 tokens/second, and request cost w = 1.0 token. Tokens refill continuously according to elapsed monotonic time:

Tokensnow = min(C, Tokensprev + Δtelapsed × r)

Requests arriving when Tokens ≥ 1.0 are admitted (HTTP 200); requests arriving when Tokens < 1.0 are rejected with HTTP 429 (RATE_LIMIT_EXCEEDED).

III. Implementation Details

The gateway (proxy-app.js) is implemented in raw Node.js (v18+) without third-party npm dependencies. Key engineering features include:

1. Stream Backpressure & Guardrails: Request bodies are streamed through a 16 KB buffer limit. Exceeding this boundary triggers stream pausing (req.pause()), socket termination (req.destroy()), and an HTTP 413 response, preventing memory exhaustion.

2. In-Memory Memory Safety: An internal garbage collector executes every 60 seconds, evicting stale client sessions and signature buckets inactive for more than 15 minutes (TTL = 15m), enforcing bounded memory overhead.

IV. Experimental Results & Verification

To evaluate the gateway against automated IP hopping, an automated load test (tests/load-test.js) dispatched 25 rapid requests with an inter-request delay of 20 ms. Each request presented a distinct simulated source IP address (10.0.0.1 through 10.0.0.25) via the X-Demo-IP header while preserving client execution cadence.

Request Index Simulated Source IP Derived Signature Token Balance Decision HTTP Status
1 10.0.0.1 e115be59193d 9.00 / 10.00 ALLOW 200 OK
2 – 9 10.0.0.2 – 10.0.0.9 e115be59193d 8.05 – 1.36 ALLOW 200 OK
10 10.0.0.10 e115be59193d 0.40 / 10.00 ALLOW 200 OK
11 10.0.0.11 e115be59193d 0.00 / 10.00 THROTTLE 429 Too Many Requests

Follow-up (t+2.5s) 10.0.0.26 e115be59193d 4.00 / 10.00 ALLOW 200 OK

As shown in Table 1, traditional rate limiters would have admitted all 25 requests because each transaction originated from an unthrottled IP address. In contrast, the cross-layer gateway identified the invariant signature (e115be59193d), exhausting the token bucket at request 10 and throttling requests 11–25. Following a 2.5-second idle pause, the bucket refilled 5.0 tokens, admitting follow-up recovery requests without signature drift.

V. Critical Limitations & Academic Disclosures

In accordance with academic rigor, the Review-1 prototype acknowledges the following constraints:

1. Network Queuing Noise: Inter-arrival jitter measurements reflect application-visible socket delivery rather than raw physical packet transmission. Router queuing delays and Wi-Fi retransmissions introduce non-deterministic noise.

2. Temporal Instability of Telemetry: Battery state represents an ephemeral thermodynamic variable, not a persistent hardware ID. Signatures remain stable across burst intervals but naturally transition over multi-hour time horizons.

3. Bucket Boundary Collisions: Coarse quantization mitigates jitter divergence but introduces a collision probability where distinct clients with identical battery states and clicking cadences map to the same token bucket.

VI. Review 2 Research Roadmap

Building upon the Review-1 foundation, the subsequent research phase will focus on:

1. Kernel Transport Hooking: Deploying eBPF and libpcap probes to inspect passive TCP handshake characteristics (TCP Window Size, TCP Options ordering, and initial SYN TTL) independent of HTTP payloads.

2. Metric-Space Clustering: Replacing rigid SHA-256 discrete bins with Locality-Sensitive Hashing (LSH) and Euclidean distance clustering over continuous feature spaces to eliminate boundary collision artifacts.
